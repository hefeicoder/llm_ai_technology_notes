Question 1
What is the harness?

The stateful system around the model: context, tools, policy, events, storage, and execution.

Question 2
Who decides what happens?

The harness decides capabilities and authority; the model chooses among advertised actions.

Question 3
What makes it production-grade?

Explicit lifetimes, bounded state, structured events, sandboxing, retries, persistence, and tests.

Vocabulary: the objects you must keep separate
Mental model before code
⌃

Most confusion comes from treating “the agent” as one thing. In Codex it is a set of objects with different lifetimes and responsibilities.

Durable
Thread

A conversation identity that can be started, resumed, forked, archived, and persisted.

User unit
Turn

Work initiated by user input and completed with a final state, usage, and zero or more items.

Stream unit
Item

A message, reasoning item, command, patch, tool call, tool result, or other observable artifact.

Inference unit
Model cycle (sampling step)

One complete request to the model and its streamed response. It may return final text or request one or more tools.

Capability
Tool

A schema shown to the model plus a runtime that can validate and execute the call.

Execution
Environment

The local or remote filesystem, process runtime, cwd, shell, workspace roots, and permissions.

Model input
Context

Base instructions, durable history, current world state, user input, and tool outputs.

Storage
Rollout

An append-oriented record used to reconstruct, inspect, resume, and migrate a thread.

Backend
Provider

Authentication, endpoint configuration, transport capabilities, model catalog, and error mapping.

“Sampling” does not mean one token. In harness code it means asking the model what to do next: send the current context and tool definitions, then stream one model response. Mentally substitute model cycle whenever you see sample or sampling step in this tutorial.

The model requests actions; the harness executes them. New tool results require another model cycle.

System architecture: six layers around a loop
The map of the repository
⌃

The core loop is small. The production architecture exists to feed that loop correct state, constrain its authority, expose its progress, and preserve its results.

In the loop below, model cycle means exactly one API request plus its streamed response. If that response requests a tool, the harness executes the tool, adds its result to context, and starts another model cycle. The loop stops when the model produces a final response with no follow-up action.
The model loop sits inside a larger operating envelope; most repository code implements that envelope.

2
One user turn, end to end
The golden path through the code
⌃

Start with one concrete scenario: “run the failing test and fix it.” The model needs multiple model cycles (called sampling steps in the code): one to request a command, then another after each new tool result until it can give a final response.

A “turn” is a loop of model cycles and tool observations, not necessarily one model request.
  1. The app-server maps v2 request fields into a core TurnInputRequest.
  2. CodexThread sends an operation into the session submission channel.
  3. The submission loop routes the operation and starts a regular session task.
  4. run_turn captures current state, records input, and enters the repeated model-cycle loop (called the sampling loop in code).
  5. The stream processor records every completed response item immediately.
  6. A tool call creates an execution future and marks the current model cycle as needing follow-up.
  7. Tool outputs are appended to history in call order, then a new model cycle begins.
  8. An assistant response with no follow-up work ends the turn.
// Conceptual shape of core/src/session/turn.rs loop { step = capture_step_context(); prompt = history.for_prompt() + step.visible_tools(); response = model.stream(prompt); for item in response.completed_items { record(item); if item.is_tool_call() { outputs.push(execute(item)); needs_follow_up = true; } } record(await_all(outputs)); if !needs_follow_up && !pending_user_input { break; } }
Immediate recording is an important reliability choice: if cancellation arrives while tools are still running, history and the rollout already agree about what the model emitted.

3
Session, turn, step, call: explicit lifetimes
Preventing stale state and cross-turn leakage
⌃

Codex makes changing state explicit by placing it in progressively shorter-lived containers. This is one of the strongest architectural patterns in the repository.

Shorter-lived state may depend on longer-lived state; the reverse dependency is dangerous.
Why session scope?
Transport and durable identity

Authentication, thread identity, persistent history, and WebSocket fallback must survive multiple user turns.

Why turn scope?
User-visible consistency

A model override, cwd, reasoning effort, permissions profile, and cancellation boundary belong to one unit of work.

Why step scope?
Atomic capability view

MCP readiness, AGENTS.md, selected roots, and tool exposure may change between model samples.

Why call scope?
Precise execution accounting

Each call needs its own id, payload, lifecycle events, cancellation, telemetry, and tool result.

The model must execute against the same tool plan it saw. ToolCallRuntime retains the originating StepContext, so a later MCP refresh cannot silently redirect an already-advertised call to a different runtime.

Context engineering: the harness’s real product
History + world state + instructions
⌃

The harness does not concatenate a few strings and call an API. It maintains a typed, ordered transcript and incrementally projects changing runtime state into model-visible items.

Base instructionsmodel template · personality
+
World statepermissions · cwd · AGENTS.md
+
Thread historymessages · calls · outputs
+
Turn injectionskills · plugins · user input
→
Model requestnormalized for modalities
Different context sources have different ownership and update rules.

World state is diffed, not constantly rewritten

Codex models changing state—model instructions, personality, AGENTS.md, permissions, environment, apps, plugins, deferred tools, collaboration mode—as structured world-state sections. The first real turn receives a full injection. Later turns receive only rendered differences plus a persisted snapshot or merge patch.

Stable prefix
Cache-friendly history

Incremental additions preserve request prefixes and improve provider-side prompt caching.

Typed fragment
Bounded context source

Each injected concept has a dedicated representation and rendering contract.

Normalization
Valid request history

Call/output pairing, unsupported modalities, ids, and oversized outputs are normalized before sampling.

Context invariants

1
Append by default

Do not rewrite prior history just because current state changed; append a delta.

2
Bound every fragment

Tool outputs, files, instructions, images, and summaries need explicit size limits.

3
Persist after projection

Record model-visible context before persisting the snapshot that claims it exists.

4
Reinject after history replacement

Compaction and rollback can invalidate baselines; the next window may need full context.

Context compaction is not “delete old messages.” It replaces history with a semantically sufficient representation, restores world-state baselines, and preserves enough metadata to resume correctly.

The model plane: selection, metadata, and transport
How a model becomes a concrete request
⌃

“Choose model X” is only the first input. Codex resolves a provider, catalog entry, capability metadata, reasoning controls, request encoding, auth, and transport.

Selection policy, model metadata, provider behavior, and transport are separate concerns.

Four cooperating abstractions

AbstractionOwnsDoes not own
ConfigLayerStackPrecedence, effective values, per-key originsModel endpoint behavior
ModelsManagerCatalog refresh/cache, defaults, metadata lookupStreaming inference
ModelProviderAuth, API provider, capabilities, error mappingConversation history

Model metadata changes harness behavior

A model catalog entry can influence context window and compaction thresholds, supported reasoning efforts, input modalities, shell and patch tool shapes, namespace and search support, personality instructions, verbosity, Responses Lite encoding, and multi-agent behavior.

The transport session is turn-scoped because sticky-routing state must be reused within a turn but never leaked into the next turn. The broader client is session-scoped so auth, provider selection, and a permanent WebSocket→HTTP fallback can survive across turns.

Why incremental WebSocket requests matter

When request properties are unchanged and the new transcript strictly extends the previous request plus response items, Codex can send only the delta with a previous response id. This turns careful context ordering into a latency and bandwidth optimization.

The tool control plane: what the model is allowed to see
Capability planning before execution
⌃

Tool selection starts before inference. Codex builds a per-step registry of executable runtimes, applies exposure policy, and derives the exact schemas advertised to the model.

A runtime can exist without being directly visible to the model.

The two halves of a tool

Control plane
ToolSpec

Name, namespace, description, argument schema, output schema, and provider wire representation.

Data plane
ToolExecutor / runtime

Argument parsing, readiness, parallelism support, hooks, lifecycle events, execution, and result conversion.

What determines availability?

  • Does the turn have an execution environment?
  • Are the relevant feature flags enabled?
  • Does the model support the tool’s wire shape?
  • Does the provider support namespaces, hosted search, or image generation?
  • Is this a root agent, subagent, or restricted guardian reviewer?
  • Are MCP servers ready, and were their capabilities selected?
  • Should the tool be direct, deferred behind search, code-mode-only, or hidden?
  • Did an external tool collide with a trusted or reserved name?
The harness chooses the menu; the model chooses an item from the menu. The model cannot grant itself a tool that was not advertised, and the registry still validates any returned name.

The tool data plane: from response item to observation
Routing, execution, and follow-up
⌃

Once the model emits a completed tool item, Codex converts it into a canonical call, schedules it, runs shared lifecycle policy, invokes a handler, and turns the result back into a Responses input item.

ResponseItemfunction/custom/search call
→
ToolCallcanonical name · call id · payload
→
Parallel gateread lock or exclusive write lock
→
Registry dispatchhooks · telemetry · handler
→
ResponseInputItemtool output for next sample
The output type closes the loop: tool execution becomes another model observation.

Parallel when safe, ordered when necessary

The response can contain multiple tool calls. A shared read/write gate allows handlers that declare parallel support to overlap, while a non-parallel tool takes an exclusive lock. Results are drained through an ordered future collection so transcript call/output relationships remain stable.

“Errors as data” is a defining agent pattern. Invalid arguments, denied actions, and command failures are usually observations the planner can reason about. Infrastructure corruption and broken invariants remain fatal.

Safety and execution: authority below the model
Approvals, policy, sandbox, and subprocesses
⌃

A coding model can propose a command, but only the execution plane can authorize and run it. Prompt instructions describe policy; the runtime enforces policy.

Approval and sandbox selection are centralized so shell and patch tools share semantics.

What unified exec owns

  • Command and cwd resolution for local or foreign environments.
  • Approval requirements derived from command policy and the active profile.
  • Filesystem and network sandbox selection.
  • PTY creation, interactive stdin, background process reuse, and bounded output.
  • Cancellation, timeouts, exit state, and sandbox-denial classification.
  • Interception of apply_patch so patch semantics stay structured.
Never rely on “the model was told not to do X.” The model-visible permission message improves planning, but the permission profile, approval flow, sandbox, and executor are the actual security boundary.

Streaming and UX: events are the interface
Decoupling core from clients
⌃

Codex does not return one final string. It emits a structured event stream that lets a TUI, IDE, SDK, or headless runner present the same work differently.

Event familyExamplesClient use
Turn lifecyclestarted, completed, aborted, errorProgress state, timing, usage, retry UI
Item lifecycleitem started/completedStable cards for messages, commands, patches, searches
Content deltasassistant text, reasoning summary, planLow-latency incremental rendering
Tool progressexec begin/output/end, patch begin/end, MCP begin/endLive terminal and action status
Human interactionapproval, permissions, user input, elicitationPause the turn and collect a typed response
Statetoken count, rate limits, turn diff, model rerouteInform navigation, warnings, and summaries

Why item lifecycle matters

A delta without an item identity is hard to reconcile, replay, or render. Codex assigns stable ids, emits item start before content, and completes the same item once finalized. App-server translates core events into v2 JSON-RPC notifications.

Interactive pauses are still tool calls

Approval and user-input tools suspend their futures while the submission loop remains able to accept the corresponding response operation. This keeps interaction inside the same turn without blocking the whole session runtime.

Treat the event stream as a public projection, not as debugging logs. It needs stable identity, ordering, terminal events, bounded queues, compatibility rules, and backpressure.

Persistence, resume, and compaction
A transcript is also a recovery log
⌃

The live prompt, durable rollout, thread catalog, and UI projection overlap—but they are not the same representation.

Different stores optimize inference, reconstruction, and browsing separately.

Resume is a semantic operation

Correct resume requires more than old chat messages. It may need base instructions, model and personality settings, dynamic tools, world-state baselines, compaction windows, MCP resource origins, and call/output relationships.

Compaction triggers

  • Before sampling when a model switch would exceed a smaller context window.
  • When the model’s compaction-compatibility hash changes.
  • Mid-turn when another follow-up is needed but token thresholds are reached.
  • Explicitly when the user or client requests compaction.
Production agents need event sourcing instincts: record enough intent and outcome to reconstruct state, while allowing derived indexes and prompt projections to evolve.

Concurrency, steering, and subagents
Many activities, one coherent transcript
⌃

Concurrency improves latency but threatens transcript order, shared state, cancellation, and authority. Codex introduces it at explicit boundaries.

Within a response
Parallel tool calls

Safe handlers overlap; exclusive handlers serialize through the runtime gate.

Within a turn
Steering and mailbox input

New user or inter-agent input can be queued and folded into a follow-up sample.

Across threads
Subagents

Separate Codex threads run concurrently with explicit parentage, communication, and status.

Subagents are threads, not recursive function calls

A spawned agent receives effective configuration, environment and permission state, provider information, parent/root turn metadata, role instructions, and a separate lifecycle. Communication is recorded as typed inter-agent items rather than mutating another agent’s hidden prompt.

Concurrency invariants

1
Every activity has a cancellation boundary

Turn cancellation propagates into sampling and tool futures.

2
Completion is explicit

A task, process, tool, response, and subagent each need a terminal state.

3
Transcript order is deterministic

Concurrent completion must not scramble the call/output structure sent back to the model.

4
Authority is inherited deliberately

A subagent does not obtain broader sandbox or approval rights merely by being spawned.

Multi-agent orchestration is an extension of the thread model: spawn, message, follow up, interrupt, list, and wait. This is easier to reason about than sharing one mutable context among concurrent planners.

Reliability, observability, and testing
Making stochastic orchestration debuggable
⌃

The model is stochastic; the harness should not be. Codex surrounds inference with deterministic event, persistence, retry, cancellation, and test boundaries.

Bound everything

ResourceBounding mechanismFailure if omitted
Conversation contextToken estimates, truncation, compaction windowsRequest rejection or unbounded cost
Tool outputByte/token caps and head-tail truncationOne command consumes the context window
ProcessesProcess count, timeouts, output buffers, cleanupResource exhaustion and leaked subprocesses
QueuesBounded transport and event channelsSlow clients exhaust server memory
RetriesProvider retry budget and transport fallbackInfinite loops and duplicate effects
ExtensionsCapability selection, collisions, readiness waitsPrompt bloat and ambiguous dispatch

Observe spans that match architectural lifetimes

Thread/session, turn, sampling attempt, response reception, tool dispatch, approval, sandbox attempt, and compaction each have distinct tracing and timing meaning. The code passes trace context through submissions and records request/tool metadata without making telemetry the source of truth.

Test at the protocol boundary

Core integration tests mount deterministic fake Responses streams, submit a real user turn, observe emitted events, inspect captured request bodies, and assert tool outputs in later requests. This tests the whole orchestration contract without a live model.

// Representative integration-test shape server.mount_sse_once([ response_created("resp-1"), function_call("call-1", "exec_command", args), response_completed("resp-1"), ]); codex.submit(user_turn).await; event = wait_for_event(exec_completed).await; request = response_mock.single_request(); assert_eq!(request.function_call_output("call-1"), expected);
The best agent tests script model behavior and assert harness behavior. Unit-testing a static tool schema is less valuable than proving that a call is exposed, executed, persisted, returned to the next sample, and surfaced to the client correctly.

Build the minimal harness—and know what is missing
Synthesis and implementation checklist
⌃

A toy harness can fit on one screen. A trustworthy harness is the list of invariants that surround that screen.

async function runTurn(userInput, state, cancel) { state.history.append(userInput); while (!cancel.requested) { // Capture one coherent view for both advertisement and execution. const step = await captureStep({ model: state.model, environment: state.environment, permissions: state.permissions, extensions: state.extensions }); const prompt = normalizeAndBound({ instructions: state.instructions, worldStateDelta: step.worldStateDelta, history: state.history, tools: step.visibleToolSpecs }); const response = await streamModel(prompt, cancel); const toolCalls = []; for await (const event of response) { emitToClient(event); if (event.completedItem) { await persist(event.completedItem); state.history.append(event.completedItem); if (event.completedItem.isToolCall) toolCalls.push(event.completedItem); } } if (toolCalls.length === 0) return finalAssistantMessage(state.history); const outputs = await executeWithPolicy(toolCalls, step, cancel); await persistInCallOrder(outputs); state.history.appendAll(outputs); maybeCompact(state); } }

State
Typed, incremental context

Stable ordering, call/output normalization, bounded fragments, compaction, resume.

Authority
Policy below inference

Tool allowlist, argument validation, approvals, permission scopes, sandbox, audit trail.

Execution
Explicit lifecycle

Ids, readiness, cancellation, timeout, progress, terminal outcome, bounded result.

Interface
Structured event stream

Typed items and deltas, backpressure, compatibility, interaction requests.

Reliability
Retry without duplicate effects

Distinguish sampling retries from tool retries; persist before crossing risky boundaries.

Verification
Scripted model integration tests

Assert requests, events, tool outputs, cancellation, persistence, and recovery.

Ten durable lessons from Codex

  1. The model is the planner; the harness is the authority.
  2. A user turn may contain many model/tool iterations.
  3. Context should be typed state with incremental projection.
  4. Advertise and execute tools from the same request snapshot.
  5. Separate tool schemas, exposure policy, routing, and execution.
  6. Treat recoverable tool failures as observations.
  7. Make session, turn, step, and call lifetimes explicit.
  8. Use structured events as the UI boundary.
  9. Persist enough information to reconstruct intent and outcome.
  10. Bound every resource and test the full loop with a fake model.
The deepest lesson is that a modern coding harness is not a clever prompt wrapper. It is a capability-secure, event-driven, persistent workflow runtime optimized for an unreliable-but-powerful planner.
