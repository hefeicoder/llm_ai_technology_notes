Question 1
What does success mean?

A response code is not enough. Consumers need to know which state now exists and which work remains.

Question 2
What should stay hidden?

Schedulers and GPU placement are implementation details. Ownership and readiness are not.

Question 3
What makes a contract durable?

Explicit identity, state transitions, failure behavior, consistency, lifecycle, and compatibility.

An API is not a collection of URLs or method signatures. It is a contract describing consumer intent, state transitions, failure behavior, consistency, lifecycle, and evolution. The schema is only the visible edge of that contract.

Python · first draft 
deployment = client.create_deployment(
    model="llama-3.1-70b",
    replicas=4,
)

response = client.generate(
    deployment=deployment.id,
    input="Explain transformers.",
)
It looks complete
Two methods, obvious nouns, pleasant defaults.

But the surface does not say whether the deployment is merely recorded, actively scheduling, or ready to serve.

Simple syntax can conceal an underspecified contract. The problem appears only when production timing, failure, and concurrency arrive.

The production incident

The first customer creates a deployment and immediately sends a generation request. The control plane has accepted the configuration, but no GPU worker is ready yet.

Incident 01 · “Created” but not serving

The client and platform both behaved as implemented. They disagreed about what the API meant.

The bug is semantic, not syntactic. Renaming the method, changing HTTP verbs, or wrapping the call in an SDK does not answer what the server guaranteed.

The anatomy of an API contract

A useful schema describes data. A production contract also describes what may happen before, during, and after every observable interaction.

Schemavalid shapes
+
State transitionswhat changes
+
Failure semanticswhat is uncertain
+
Consistencywhen reads agree
+
Lifecyclewho owns work
+
Compatibilityhow it evolves
The schema is necessary. The other five terms determine whether the API remains trustworthy in production.
State
What became true?

Was intent recorded, capacity allocated, or readiness achieved?

Time
When is it observable?

Does the next read reflect the write? Can status legitimately lag?

Failure
What remains uncertain?

Did the work happen even though the response was lost?

Ownership
Who owns the work?

Does work survive disconnect, timeout, or client process death?

Identity
What is the same thing?

Resource, logical action, transport attempt, and result need distinct identities.

Evolution
What may safely change?

Consumers will persist values and assumptions the service can no longer coordinate.

Control plane and data plane

Inference platforms expose two kinds of work with different latency, durability, and ownership expectations. Mixing them into one mental model creates bad defaults.

Resource, operation, or request?

The public abstraction should match the consumer’s mental model and the work’s lifetime, not the backend service that happens to execute it today.

Model revisionImmutable identity used for reproducibility
DeploymentDurable desired serving configuration
OperationDurable observation of control-plane work
→
Generation requestEphemeral caller-owned inference work
Generation identityAdded when replay, accounting, or observation requires it
Stream and terminal resultPartial observations plus one explicit outcome
Identity follows the abstraction’s lifetime. It should not expose scheduler job IDs or machine placement.
Use a resource when
The user expects durable state.

It can be named, retrieved, updated, observed, and eventually deleted.

Use an operation when
Work outlives one request.

The consumer needs durable progress, terminal result, error, or cancellation.

Use a request when
The interaction owns the work.

The result is immediate or streamed and persistence is not part of the promise.

Design from consumer intent

The consumer wants a model served with a capacity policy. It does not want to become a client of the scheduler, capacity allocator, model loader, and health checker.

Backend mechanics leak
Imperative orchestration API
  • reserve_gpu_pool()
  • submit_scheduler_job()
  • load_model_on_workers()
  • register_serving_route()
→
Consumer intent survives
Declarative deployment resource
  • model revision or resolvable alias
  • fixed or autoscaling capacity policy
  • durable resource identity
  • observable readiness status
Hide complexity, not semantics. Consumers should not know which scheduler or GPU host is involved. They must know whether desired state was accepted and whether serving capacity is ready.

This contract is intentionally incomplete. We have defined what the resource means, but not yet safe retries, lost responses, concurrent updates, or durable operation tracking. Those ambiguities drive Chapters 2–4.

The server obligation

A clean response shape is not enough. The implementation must make the public guarantee true at the service boundary.

Server pseudocode · conceptual 
def create_deployment(request, principal):
    reject_output_only_fields(request, ["name", "status"])
    validate_exactly_one_capacity_policy(request.capacity)

    model_revision = resolve_model_alias(request.model)
    deployment_name = allocate_resource_name(principal.tenant)

    deployment = Deployment(
        name=deployment_name,
        model=model_revision.name,      # immutable revision
        capacity=request.capacity,      # desired state
        status=Status(phase="PENDING"), # output-only
    )

    with durable_store.transaction():
        durable_store.insert(deployment)
        durable_store.append_reconcile_intent(deployment.name)
    return created(deployment)

The scheduler may be replaced later. The consumer contract remains stable because the server exposes a Deployment and its status—not the queue, worker, or cluster that implements it.

Test the boundary, not the implementation

Contract tests should assert externally observable guarantees. They should not freeze scheduler calls, database tables, or other implementation details.

pytest-style contract tests 
def test_status_is_output_only(api):
    response = api.post("/v1/deployments", json={
        "model": "llama-3.1-70b",
        "capacity": {"fixed_replicas": 4},
        "status": {"phase": "READY"},
    })

    assert response.status_code == 400
pytest-style contract tests 
def test_alias_resolves_to_revision(api):
    deployment = create_deployment(
        api,
        model="llama-3.1-70b",
    )

    assert deployment["model"] \
        == "models/llama-3.1-70b@2026-08-01"
    assert "scheduler_job_id" \
        not in deployment
✓

The client cannot set server-owned status or resource identity.

✓
Reproducibility test

✓
Abstraction test

The public resource does not leak scheduler, cluster, host, or GPU-pool identifiers.

State the guarantee explicitly

Chapter 1 guarantee

A successful CreateDeployment response means a named Deployment resource now exists with durable desired configuration and a resolved model revision. It does not mean serving replicas are ready; readiness is reported separately through output-only status.

Design checklist

What durable state exists when the call returns?
Which fields express consumer intent?
Which fields are output-only observations?
What is a resource, operation, or transient request?
Which internal identifiers must stay hidden?
Does “success” imply existence, progress, or readiness?
